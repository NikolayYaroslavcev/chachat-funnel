# ChaChat Funnel — Specification

Статус: draft-before-implementation. Написано до начала работы над кодом.
Основано на: `docs/product-research.md` и `docs/plan-testovogo-zadaniya.md` (последний фиксирует систематизированные требования тестового задания и используется как источник требований компании, поскольку отдельного файла с оригинальным текстом задания в репозитории нет).

Этот документ описывает **ожидаемое поведение системы**, а не её реализацию. Там, где способ реализации не является требованием, документ намеренно оставляет свободу выбора (см. раздел 20).

## 1. Purpose / Scope

### Цель проекта

Небольшой full-stack web funnel для продукта ChaChat: `Start → Quiz → Email → Paywall → Payment → Install`. Цель тестового задания — не визуальная полировка, а корректность пользовательского сценария, identity, attribution, аналитики и платёжной логики, включая конкурентные и повторные запросы.

### В scope

- Шесть экранов funnel и переходы между ними.
- Anonymous visitor → identified user lifecycle, включая случай "email уже существует".
- Сохранение attribution (UTM, referrer, landing URL).
- Запись meaningful funnel events в PostgreSQL.
- Data model, поддерживающая funnel-аналитику через SQL.
- Три payment plans, custom payment form (без внешнего redirect).
- Fake PSP с детерминированными success / decline / timeout.
- Гарантия отсутствия дублирующих успешных покупок при double-click, двух вкладках, refresh, повторной отправке запроса.
- Docker Compose запуск с чистого состояния, автоматические миграции.
- README (SQL-примеры, test card rules), agent instructions.

### Вне scope (сознательно не реализуется)

- Login/authentication, аккаунты, восстановление пароля.
- Реальный payment processor, PCI-совместимость, реальные платежи.
- Реальная отправка email (transactional email/SMTP).
- Реальный app distribution — Install даёт ссылку на существующие публичные страницы ChaChat, не создаёт новый билд.
- Кросс-девайс identity resolution (recognition работает только в рамках одного браузера/cookie).
- Управление подпиской после покупки: апгрейд/даунгрейд/отмена/refund.
- Промокоды, скидки, мультивалютность.
- Админ-панель, CMS, feature flags, A/B testing.
- i18n / локализация.
- Полное покрытие тестами всего проекта — только критическая payment-логика.

Эти пункты не добавляются "на всякий случай" даже если технически просты — они не требуются заданием.

## 2. Product context

ChaChat — AI companion / roleplay chat продукт (web/iOS/Android, 18+, Lifestyle). Подтверждённые фичи, которые можно использовать как факты в quiz/paywall: библиотека AI-персонажей, кастомные персонажи с возможностью поделиться, текстовый чат с "памятью" предыдущих разговоров, голосовые звонки, генерация изображений по контексту разговора, ролевые/story-сценарии, виртуальная валюта ("gems") поверх подписки.

Не подтверждено и не используется как факт: конкретные модели ИИ, точные free-tier лимиты, групповые чаты, интеграции с другими платформами, официальная тарифная сетка.

Тон quiz/paywall — нейтральный, "safe for review": продукт 18+ и включает романтический roleplay, но контент тестового задания не должен явно уходить в sexual framing.

Полное продуктовое обоснование — в `docs/product-research.md`, разделы 1–2, 7.

## 3. Tech stack

Зафиксировано как обязательное:

- **Next.js** (**App Router**) — единственный framework для frontend и backend (API/server-side операции), включая payment flow.
- **TypeScript** — весь код.
- **PostgreSQL** — единственное хранилище данных funnel/identity/analytics/payments.
- **Docker Compose** — единая точка запуска (`docker compose up`) приложения и PostgreSQL с чистого checkout, миграции применяются автоматически при старте.

Намеренно НЕ зафиксировано на этом этапе (решается при реализации, см. раздел 20):

- Конкретный ORM/DB client.
- Способ организации API-роутов внутри App Router.
- Механизм anonymous identity на клиенте (какой именно cookie/storage).
- Механизм idempotency/блокировок на уровне БД.
- Конкретные тестовые номера карт fake PSP.

## 4. Funnel specification

Единственно допустимая последовательность экранов:

```
Start → Quiz → Email → Paywall → Payment → Install
```

### Общие правила переходов

- Переходы вперёд разрешены только при выполнении условия перехода данного экрана (см. ниже для каждого экрана).
- Прямой переход на экран из середины funnel (без прохождения предыдущих обязательных шагов) **не допускается** для новой identity — сервер обязан проверять предпосылки (например, нельзя попасть на Paywall без email, нельзя попасть на Payment без выбранного plan, нельзя попасть на Install без успешной покупки), а не полагаться только на клиентскую навигацию.
- Исключение: уже identified/purchased пользователь может напрямую попасть на Install при заходе в funnel заново — см. раздел 7.
- Возврат назад по экранам (Quiz ⇄ Email ⇄ Paywall) для ещё не купившего пользователя допустим на уровне UI и не является ошибкой; предыдущие данные (ответы, email) не должны затираться пустыми значениями при просто повторном просмотре экрана.

### 4.1 Start

- **Назначение**: объяснить продукт, дать причину продолжить, единственный CTA — начать quiz.
- **Пользователь видит**: позиционирование ChaChat, value proposition, CTA "Start"/"Continue".
- **Действие**: клик по CTA.
- **Данные**: создаётся anonymous visitor + session, если их ещё нет (см. раздел 5); фиксируется attribution, если это первая session визитора (раздел 8).
- **События**: `screen_view` (screen=start).
- **Условие перехода дальше**: клик по CTA. Никаких предварительных условий не требуется — Start доступен всем.
- **Ошибки/альтернативные состояния**: нет специфичных ошибок; технический сбой создания visitor/session — общий error handling (раздел 17).

### 4.2 Quiz

- **Назначение**: собрать интересы пользователя и одновременно продемонстрировать продукт (см. раздел 15).
- **Пользователь видит**: последовательность вопросов (3–7, финальный список — раздел 15), по одному на шаг.
- **Действие**: выбирает ответ на каждом шаге.
- **Данные**: quiz answer сохраняется при ответе на каждый вопрос (не только в конце квиза).
- **События**: `screen_view` (screen=quiz, step=N) при показе шага; `quiz_answer_submitted` при ответе; `quiz_completed` после последнего вопроса.
- **Условие перехода дальше**: все вопросы отвечены.
- **Ошибки/альтернативные состояния**: повторное открытие того же шага (back/refresh) показывает ранее выбранный ответ, если он есть, и не создаёт дублирующую запись ответа — повторный ответ на тот же вопрос в рамках той же session обновляет существующий, а не добавляет новый (см. раздел 9, quiz_answers).

### 4.3 Email

- **Назначение**: идентифицировать пользователя перед paywall.
- **Пользователь видит**: форму ввода email.
- **Действие**: вводит email, отправляет форму.
- **Данные**: при успешной отправке anonymous visitor привязывается к identified user (новому или существующему) — полная логика в разделах 5–6.
- **События**: `email_submitted` (с признаком new/existing).
- **Условие перехода дальше**: email прошёл валидацию формата и запрос на identify/link завершился успешно.
- **Ошибки/альтернативные состояния**: невалидный формат email — inline-ошибка, экран не покидается; серверная ошибка при linking — контролируемая ошибка, пользователь может повторить отправку без потери введённого значения; повторная отправка того же email (double submit) — идемпотентна, не создаёт вторую identity.

### 4.4 Paywall

- **Назначение**: продать один из трёх планов.
- **Пользователь видит**: три плана (название/цена/условия), явные различия, custom payment form.
- **Действие**: выбирает план, заполняет card number/expiry/CVC, нажимает Purchase.
- **Данные**: выбор плана фиксируется; отправка формы создаёт payment attempt.
- **События**: `screen_view` (screen=paywall); `plan_selected`; `purchase_attempted` при нажатии Purchase.
- **Условие перехода дальше** (на Payment-обработку/дальше к Install): см. payment state machine, раздел 11. Paywall доступен только identified пользователю (email уже известен) — прямой заход без email недопустим (redirect на Email).
- **Ошибки/альтернативные состояния**: детально в разделах 11–12 и 14 (loading/decline/timeout/retry состояния формы).

### 4.5 Payment

Payment — не отдельный самостоятельный "экран" с собственным URL, а состояние обработки purchase-запроса, инициированного с Paywall (custom form остаётся на той же странице, состояние формы меняется: submitting → success/decline/timeout). Формально выделено отдельным пунктом funnel, потому что имеет собственный жизненный цикл данных (payment attempt), не сводящийся к UI paywall.

- **Назначение**: провести оплату через fake PSP и получить детерминированный результат.
- **Пользователь видит**: loading/submitting состояние на paywall-форме, затем success или error UI.
- **Действие**: пользователь ждёт результат; при decline/timeout может повторить (retry).
- **Данные**: payment attempt переходит по состояниям (раздел 11); при success создаётся purchase.
- **События**: `purchase_succeeded` или `purchase_failed` (с причиной).
- **Условие перехода дальше (к Install)**: payment attempt достиг состояния `succeeded`.
- **Ошибки/альтернативные состояния**: decline / timeout / unexpected error — раздел 11–12; конкурентные сценарии — раздел 13.

### 4.6 Install

- **Назначение**: подтвердить покупку и направить пользователя к самому продукту.
- **Пользователь видит**: подтверждение успешной покупки, CTA/ссылка на приложение, упоминание email.
- **Действие**: переход по ссылке (вне funnel).
- **Данные**: не создаёт новых сущностей, только читает состояние покупки.
- **События**: `screen_view` (screen=install).
- **Условие перехода/доступа**: у текущей identity (visitor→user) есть хотя бы одна purchase со статусом succeeded. Иначе — раздел 16.
- **Ошибки/альтернативные состояния**: попытка доступа без покупки — раздел 16.

### Недопустимые переходы (явно)

- Email → Paywall без успешного email submit.
- Paywall/Payment → Install без успешной purchase.
- Прямой заход на Payment без выбранного plan.
- Повторное списание по той же логической payment operation (см. раздел 13).

## 5. User identity lifecycle

Жизненный цикл: `anonymous visitor → session/history → email → identified user → purchase`.

### Ключевые сущности identity (логически, без деталей реализации)

- **Visitor** — устойчивая (persisted, cross-session) анонимная identity, привязанная к браузеру/устройству через клиентский идентификатор (например, cookie), создаётся при первом обращении к funnel. Именно visitor — держатель до-email истории (quiz answers, events), а не session.
- **Session** — ограниченный по времени визит в рамках одного visitor (раздел 7). Attribution фиксируется на уровне session.
- **User** — identified пользователь, появляется в момент успешной отправки email. Ровно один email = ровно один user.

Связь: `visitor.user_id` — nullable ссылка на user, устанавливается один раз (или переустанавливается на того же user повторно — идемпотентно) в момент email submit.

### Новый посетитель (первый визит)

При первом обращении к funnel (нет валидного visitor-идентификатора у клиента):

- Создаётся новый visitor и новая session.
- Фиксируется attribution текущей session (раздел 8).
- Вся последующая активность (screen views, quiz answers, funnel events) до момента email привязывается к этому visitor/session.

### Anonymous → новый email

Email не найден среди существующих users:

- Создаётся новый user с этим email.
- `visitor.user_id` устанавливается на этого нового user.
- Вся уже накопленная anonymous-история (quiz answers, events, attribution текущей и прошлых sessions этого visitor) становится историей нового user **через существующую связь visitor→session→события**, без копирования и без дублирования записей.

### Anonymous → существующий email (критический случай)

Email найден среди существующих users. Требование задания: история текущего anonymous visitor не должна теряться и не должна порождать дублирующего пользователя.

Определённое поведение:

- **Итоговая identity** — существующий user. Новый user НЕ создаётся.
- `visitor.user_id` текущего anonymous visitor устанавливается на найденного существующего user (а не создаётся отдельный "второй" пользователь и не запускается процедура слияния двух полноценных users — предпочтительная концепция именно связывание, а не merge).
- **Session** — текущая session не пересоздаётся; она остаётся как есть и теперь принадлежит (через visitor) идентифицированному существующему user.
- **Quiz answers** текущей session/visitor — сохраняются без изменений, физически не перемещаются и не копируются; они становятся частью истории existing user благодаря связке visitor→user.
- **Funnel events** текущей session/visitor — аналогично сохраняются как есть и становятся видимы в истории existing user.
- **Attribution** — attribution текущей session сохраняется как есть (эта конкретная сессия действительно пришла с этими UTM/referrer); она НЕ становится "новым first-touch" existing user — canonical acquisition attribution для user определяется как attribution самой первой session во всей его истории (раздел 8). Так old user не теряет свой исходный источник привлечения, а новая session просто добавляется как ещё одна запись в его истории визитов.
- **Существующие purchases** найденного user — не изменяются, не дублируются, продолжают принадлежать этому user; они становятся видимы в контексте текущей identity (например, для проверки доступа к Install — если у user уже была успешная покупка, Install становится доступен немедленно, повторная оплата не требуется, см. раздел 7).
- **Повторная отправка того же email** (в рамках той же или другой session этого же уже-привязанного visitor) — идемпотентна: результат линковки тот же (тот же user), повторного создания/повторной привязки не происходит, дублирующих строк связи не появляется.
- **Ограничения целостности**: `users.email` уникален; `visitor.user_id` может указывать только на один user одновременно и не может "переключаться" на другого user после того как уже установлен на конкретного (иначе более ранняя anonymous-история visitor стала бы историей чужого пользователя) — единственное разрешённое повторное присвоение `visitor.user_id` — присвоение того же значения (идемпотентный no-op).

### Повторная отправка того же email в рамках ещё не идентифицированного visitor

Если `visitor.user_id` уже установлен (на любого user, нового или существующего) и с той же visitor identity снова отправляется email:

- Если это тот же email — no-op, идентичный результат.
- Если это другой email — это редкий/пограничный сценарий (пользователь передумал). Поведение: система не выполняет "переподключение" истории уже привязанного visitor к другому user (см. ограничение целостности выше). Вместо этого система должна начать новую anonymous identity/session для нового email, чтобы не исказить историю уже сформированной identity. Это намеренно консервативное решение — приоритет отдаётся целостности уже установленной связи visitor↔user, а не гибкости "поменять email в процессе". Отмечено как решение, принятое в спецификации (раздел 21).

## 6. Existing email behavior (сводка)

Данный раздел суммирует поведение, детально описанное в разделе 5, как отдельный явно проверяемый сценарий (это отдельное обязательное требование задания).

При email submit система обязана:

1. Определить, существует ли user с этим email (case-insensitive сравнение — email не должен различаться по регистру для целей идентичности).
2. Если существует — связать текущего anonymous visitor с этим user, не создавая нового user.
3. Сохранить всю anonymous-историю текущего visitor доступной в истории existing user.
4. Не терять и не дублировать существующие purchases найденного user.
5. Обеспечить, что повторная отправка того же email идемпотентна.
6. Отправить `email_submitted` со свойством, различающим new/existing (нужно для аналитики — раздел 10).

## 7. Sessions / repeat visits

Три разных понятия, которые не должны смешиваться:

- **Продолжение текущего funnel** — пользователь перемещается между экранами funnel в рамках одной активной session (тот же visitor, session не истекла). Данные (quiz answers, email, выбранный plan) сохраняются между экранами без потерь; refresh страницы не создаёт новую session и не сбрасывает прогресс.
- **Повторный визит** — тот же visitor (распознан по клиентскому идентификатору), но текущая session истекла (по неактивности) или отсутствует → создаётся **новая session** для того же visitor. Attribution фиксируется заново для этой новой session (раздел 8), но не переопределяет canonical first-touch existing user.
- **Новая session (новый visitor)** — клиентский идентификатор отсутствует или не распознан (другой браузер/устройство, очищенные cookies) → создаётся новый visitor + новая session, воспринимается системой как первый визит, даже если по email это тот же реальный человек (recognition для этого случая работает только через существующий-email flow на экране Email, не автоматически — это задокументированное ограничение, см. раздел 1).

### Порог "истечения" session

Session считается истёкшей при отсутствии активности в течение 30 минут (значение по умолчанию, конкретное число — деталь реализации, не критичная для бизнес-корректности; см. раздел 20).

### Поведение при повторном визите после того, как email уже известен

Аккаунтная система не создаётся, но funnel обязан использовать уже известную identity, чтобы не заставлять пользователя проходить всё заново без необходимости:

- Если у идентифицированного (через visitor→user) пользователя уже есть purchase со статусом `succeeded` — при заходе в funnel пользователь направляется сразу на Install (независимо от того, с какого экрана начался повторный визит), повторная оплата не требуется и не предлагается как обязательный шаг.
- Если email уже известен, но успешной покупки ещё нет — funnel не требует повторного прохождения Quiz/Email принудительно, если пользователь снова доходит до экрана Email: тот же email просто подтверждает уже существующую связь (идемпотентно, раздел 5) и пользователь продолжает на Paywall. Явного автоматического "прыжка" сразу на Paywall при заходе на Start не требуется — это осознанно не специфицируется как обязательное поведение (не запрошено заданием), чтобы не вводить логику, эквивалентную account/session restore system.
- Новая session у уже идентифицированного visitor создаёт новые quiz answers (новые ответы на этот заход), не перезаписывая ответы прошлой session — обе session отдельно видны в истории.

## 8. Attribution

Сохраняются: UTM parameters (`utm_source`, `utm_medium`, `utm_campaign`, `utm_term`, `utm_content`), `referrer`, `landing_url`.

### Правила

- **Момент фиксации**: attribution фиксируется один раз при создании session — на основании параметров самого первого запроса этой session (UTM в query string, `Referer` header, полный landing URL). Действие относится к **session**, а не напрямую к visitor или к user — это её естественная гранулярность, потому что у одного visitor/user может быть несколько session с разными источниками привлечения.
- **Перезапись**: attribution конкретной session после фиксации не перезаписывается — повторная навигация внутри той же session другими ссылками/UTM не меняет уже сохранённые значения (иначе first-touch этой session терялся бы). Каждая новая session (в том числе повторный визит) фиксирует свою собственную attribution — старые значения не трогаются.
- **Связь с итоговым user**: canonical acquisition attribution пользователя (для аналитики "acquisition by UTM", "revenue by plan/source" и т.п.) определяется как attribution **самой первой по времени session** среди всех session, чей visitor в итоге связан с этим user (first-touch across full history). Это вычисляемое правило (`MIN(session.started_at)` по всем session, приведённым к user через visitor), а не отдельно копируемое поле — то есть отдельного "перезаписываемого" attribution-поля на user нет.
- **Anonymous → identified (включая existing email)**: при линковке attribution ничего не меняет и не переносится специально — она уже находится на session, а session уже связана с visitor, который теперь связан с user. Для нового user текущая session и есть его first-touch. Для существующего user текущая session становится дополнительной (non-first) записью в его истории посещений, что и требуется по правилу выше.

## 9. Data model

Логические сущности (без SQL/DDL).

### `users`
- Назначение: identified пользователь funnel.
- Ключевые данные: email (уникален, case-insensitive), created_at.
- Связи: 1—N с `visitors` (через `visitor.user_id`), 1—N с `payment_attempts`, 1—N с `purchases` (через attempts).
- Целостность: email уникален; email не может быть пустым/невалидным на момент создания user.
- Для аналитики: created_at даёт момент идентификации; email_domain может использоваться для сегментации без хранения PII в аналитике, если потребуется.

### `visitors` (anonymous identity)
- Назначение: устойчивая cross-session анонимная identity, держатель до-email истории.
- Ключевые данные: client-facing идентификатор (opaque token), created_at (первый визит), `user_id` (nullable).
- Связи: 1—N с `sessions`; опционально N—1 с `users`.
- Целостность: `user_id`, будучи установленным, не может быть переустановлен на другого user (см. раздел 5).

### `sessions`
- Назначение: единица "визита", держатель attribution.
- Ключевые данные: visitor_id, started_at, last_activity_at, attribution-поля (utm_*, referrer, landing_url), опционально user_agent.
- Связи: N—1 с `visitors`; 1—N с `quiz_answers`, `funnel_events`.
- Целостность: attribution-поля неизменяемы после первой записи в рамках session.
- Для аналитики: session — единица группировки screen-view последовательности и attribution-разрезов (acquisition by UTM).

### `quiz_answers`
- Назначение: ответы пользователя на quiz.
- Ключевые данные: session_id, question_key, answer_value, answered_at.
- Связи: N—1 с `sessions` (через session — N—1 с `visitors`).
- Целостность: не более одной актуальной записи на пару (session, question) — повторный ответ обновляет, не дублирует (см. раздел 4.2).
- Для аналитики: quiz drop-off по question_key.

### `funnel_events`
- Назначение: единый лог всех meaningful событий (раздел 10).
- Ключевые данные: session_id, event_name, occurred_at, свойства события (структурированные, специфичные для event_name), опциональные ссылки на связанные сущности (payment_attempt_id, purchase_id, plan_id — когда применимо).
- Связи: N—1 с `sessions` (⇒ транзитивно с visitor/user).
- Целостность: события неизменяемы после записи (append-only).
- Для аналитики: основной источник funnel-последовательности, конверсии, drop-off.

### `plans`
- Назначение: справочник из трёх тарифов.
- Ключевые данные: slug/название, цена, валюта, billing period, порядок отображения, активность.
- Связи: 1—N с `payment_attempts`/`purchases`.
- Целостность: неизменяемая reference-таблица (seed data), не создаётся пользователями.

### `payment_attempts`
- Назначение: каждая попытка оплаты — как успешная, так и нет; единица payment state machine и idempotency.
- Ключевые данные: user_id (payment требует identified user), plan_id, idempotency key (логическая, значение/механизм — раздел 13), status, created_at, updated_at, completed_at, fake-PSP-специфичные данные результата (например маскированный номер карты, причина отказа).
- Связи: N—1 с `users`, N—1 с `plans`; 1—1 (опционально) с `purchases`.
- Целостность: не более одного активного (нетерминального) attempt на user одновременно (раздел 13); статус меняется только вперёд по допустимым переходам (раздел 11), назад — никогда.
- Для payment flow: единственный источник правды о том, что происходило с конкретной попыткой оплаты.

### `purchases`
- Назначение: только успешно завершённые покупки.
- Ключевые данные: payment_attempt_id (уникально — 1 purchase на 1 successful attempt), user_id, plan_id, amount, currency, purchased_at.
- Связи: 1—1 с `payment_attempts` (только succeeded), N—1 с `users`, N—1 с `plans`.
- Целостность: создаётся исключительно атомарно вместе с переходом attempt в succeeded; не может существовать purchase без succeeded attempt и не может быть двух purchases на один attempt.
- Для payment flow / analytics: единственный источник правды о доступе к Install и о revenue.

Полная восстановимая цепочка: `visitor → session → funnel_events/quiz_answers → (email) → user → payment_attempts → purchases`.

События позволяют отвечать на: funnel drop-off по шагам, quiz per-question drop-off, email conversion (new vs existing split), plan popularity, payment success rate, revenue by plan, acquisition by UTM/referrer (через join до session), полное восстановление истории конкретного user.

## 11. Payment states and flow

### Состояния (payment_attempts.status)

```
initiated → processing → succeeded
                       → declined
                       → timed_out
                       → errored
initiated → errored   (stage 12: reap edge — см. раздел 13, "Реализация")
```

- `initiated` — attempt создан (сервер принял запрос на покупку), ещё не отправлен в fake PSP.
- `processing` — запрос отправлен в fake PSP, ожидается результат.
- `succeeded`, `declined`, `timed_out`, `errored` — терминальные состояния. Из терминального состояния возврата к `processing`/`initiated` того же attempt нет.

### Переходы

- Разрешено: `initiated → processing`, `processing → succeeded|declined|timed_out|errored`, и (stage 12) `initiated → errored` — исключительно для reap уже покинутого клиентом/процессом attempt, не для обхода `processing` при реальном PSP-исходе.
- Запрещено: любой переход из терминального состояния; пропуск `processing` при переходе в терминальное состояние по результату PSP (даже мгновенный fake PSP ответ логически проходит через `processing`, даже если это происходит быстро) — единственное исключение из этого правила — reap-переход выше, который не является PSP-исходом.

### Purchase creation

- `purchase` создаётся строго в момент и атомарно с переходом attempt в `succeeded`. Не раньше (не на `initiated`/`processing`) и не отдельным шагом позже.
- Purchase считается успешной сразу по факту существования записи (нет отдельного "подтверждающего" шага) — succeeded attempt ⇒ существующая purchase, это одно и то же событие с точки зрения бизнес-логики.
- Install становится доступен, как только purchase создана (раздел 4.6, 16).

### Retry

- Retry разрешён только после того, как предыдущий attempt для этой логической покупки достиг терминального failure-состояния (declined/timed_out/errored).
- Retry — это **новый** payment_attempt (новая логическая операция в терминах idempotency, раздел 13), не изменение старого. Старый attempt остаётся в БД неизменным как есть (для аналитики: сколько попыток потребовалось до успеха).
- Retry после `succeeded` не имеет смысла (Install уже доступен) и не должен предлагаться UI как основной путь — не запрещается как техническая операция (не входит в обязательный scope запрещать повторную покупку другого плана), но не является частью обязательного сценария.

### Success / decline / timeout / error — что происходит

- **Success**: attempt → `succeeded`; purchase создаётся; `purchase_succeeded` событие; доступ к Install открыт.
- **Decline**: attempt → `declined`; purchase не создаётся; `purchase_failed` (reason=declined); пользователь остаётся на Paywall, форма показывает понятную ошибку, retry разрешён.
- **Timeout**: fake PSP не отвечает в пределах ограниченного времени ожидания → attempt → `timed_out` (не остаётся в `processing` бесконечно); purchase не создаётся; `purchase_failed` (reason=timed_out); UI не показывает бесконечный spinner, показывает понятное состояние с возможностью retry.
- **Unexpected error**: любая непредвиденная ошибка при обработке (не штатный decline/timeout от fake PSP) → attempt → `errored`; purchase не создаётся; состояние БД остаётся консистентным (см. правило атомарности ниже); `purchase_failed` (reason=errored); retry разрешён.

### Консистентность БД

Переход attempt в терминальное состояние и (при success) создание purchase — атомарная операция: не может существовать succeeded attempt без purchase, и не может существовать purchase без ровно одного succeeded attempt. При сбое в середине операции система должна откатиться к последнему согласованному состоянию (attempt остаётся в дотерминальном состоянии, отдельного "полузаписанного" purchase не появляется), а не оставлять частично применённые изменения.

## 12. Fake PSP behavior

Требования:

- Fake PSP воспроизводимо поддерживает как минимум три исхода: success, decline, timeout.
- Результат детерминирован входными данными (тестовым номером карты и/или другим полем формы), а не случаен и не зависит от таймингов запроса.
- Правила должны быть реализованы на backend (fake PSP — серверный модуль), не в UI — то есть даже запрос в обход UI, с тем же тестовым номером карты, обязан давать тот же результат.
- Правила документируются в README (конкретные номера карт фиксируются на этапе реализации).
- Timeout — реальный ограниченный по времени исход (симулированная задержка сверх которой fake PSP явно возвращает timeout), а не бесконечное ожидание.

Конкретные номера тестовых карт, длительность симулированной задержки для timeout — детали реализации (раздел 20), но их наличие и детерминированность — обязательное требование.

Реализация и конкретные номера карт: `lib/fake-psp.ts`, задокументированы в `docs/fake-psp.md`.

## 13. Concurrency / idempotency requirements

### Определение "одной логической payment operation"

Одна логическая payment operation — это единственная активная попытка оплаты для данного identified user в конкретный момент времени. Формально: **у одного user не может существовать более одного payment_attempt в нетерминальном состоянии (`initiated` или `processing`) одновременно.** Любой запрос на покупку, поступивший, пока для этого user уже существует нетерминальный attempt, относится к ЭТОЙ ЖЕ операции, а не порождает новую.

Это определение сознательно не завязано на клиентский idempotency-key как единственный механизм распознавания дубликата — оно завязано на состояние на сервере/БД (per user), что явно требуется заданием ("защита на уровне backend/database, а не только UI") и устойчиво к сценариям, где клиент физически не может гарантированно передать один и тот же key (два независимых browser tab).

### Что считается новой операцией vs повтором vs retry vs дублем

- **Новая payment operation** — запрос на покупку, когда для user нет ни одного нетерминального attempt (первая попытка, либо предыдущая уже завершилась success/decline/timeout/error).
- **Повтор существующей операции / дублирующий запрос** — запрос на покупку, поступивший, пока для user уже есть нетерминальный attempt. Система обязана: не создавать второй attempt, не инициировать вторую отправку в fake PSP, а вернуть/отразить клиенту состояние уже существующей операции (её текущий или итоговый статус).
- **Допустимый retry** — новая payment operation, инициированная ПОСЛЕ того, как предыдущий attempt того же user достиг терминального failure-состояния. Отличается от "дублирующего запроса" тем, что предыдущая операция уже закрыта — новый attempt не конфликтует с активной.

### Сценарии

- **Double-click**: два почти одновременных запроса на покупку от одного user. Первый создаёт/продолжает нетерминальный attempt; второй распознаётся как повтор этой же операции (правило выше) → не создаёт второй attempt → максимум один succeeded attempt/purchase в итоге.
- **Two tabs**: то же самое, только источник двух запросов — разные вкладки/разные клиентские сессии одного и того же identified user. Правило "не более одного нетерминального attempt на user" покрывает и этот случай, поскольку оно завязано на user, а не на конкретную вкладку/клиентский key.
- **Refresh**: пользователь обновляет страницу, пока attempt в `processing`. При повторной загрузке paywall система обязана отразить фактическое (текущее либо уже терминальное) состояние существующего attempt этого user, а не предложить создать новый запрос как будто оплаты ещё не было.
- **Repeated request**: клиент явно повторно отправляет тот же payment request (например, повторный POST после отсутствия ответа). Обрабатывается тем же правилом — если для user уже есть attempt (нетерминальный или уже завершившийся результатом этого самого запроса), повторный запрос не создаёт новый attempt/purchase, а возвращает фактический результат.
- **Network failure** (backend обработал, клиент не получил ответ): backend уже мог перевести attempt в терминальное состояние до разрыва соединения. Последующий запрос клиента (ретрай тем же или новым HTTP-запросом) обязан обнаружить уже существующий (возможно уже терминальный) attempt и вернуть его фактический результат, а не создать новый attempt и не повторно отправлять запрос в fake PSP.

### Главная гарантия

> Один логический payment operation не должен приводить к двум успешным purchases.

Формально: для одного user в любой момент времени существует не более одной `succeeded` purchase, порождённой одной и той же логической операцией; в целом по всем retry-циклам количество `succeeded` purchases равно количеству реально доведённых до успеха логических операций (по одной purchase на успешную операцию), без дублей от double-click/two tabs/refresh/repeated request. При этом повторная попытка оплаты **после decline/timeout/error** — легитимная новая операция и должна быть разрешена (не путать с дублирующим запросом активной операции).

Технический механизм обеспечения этой гарантии (constraint на уровне БД, блокировка строки, сериализация транзакций и т.п.) не фиксируется здесь — фиксируется только требуемый результат и то, что он должен обеспечиваться на backend/DB уровне, не только отключением кнопки в UI.

### Реализация (stage 12)

Механизм, которым фактически обеспечена гарантия из этого раздела:

- **Активная операция** (double-click, two tabs, request поверх ещё не завершённого attempt): партиционный unique index `payment_attempts_one_active_per_user` (см. раздел 9, `payment_attempts`) — не более одного `initiated`/`processing` attempt на user одновременно. `lib/payment.ts` сначала читает существующий активный attempt (быстрый путь), но фактическую гарантию под конкурентной нагрузкой даёт именно constraint: проигравший конкурентный INSERT ловится по коду ошибки уникальности и превращается в результат "эта же операция", а не в 500.
- **Повтор уже завершённой операции** (client retry после network failure, resume после refresh уже после того, как attempt стал terminal): раздел 13 сознательно не полагается на клиентский ключ как единственный механизм, но и не запрещает использовать его как дополнительный — добавлено поле `payment_attempts.idempotency_key` (nullable, unique per user — см. раздел 9) и опциональное поле `idempotencyKey` в теле `POST /api/purchase`. Если ключ совпадает с уже существующим attempt (любого статуса, не только активного), запрос присоединяется к нему вместо создания нового. Отсутствие ключа не ослабляет гарантию для активной операции (constraint выше работает независимо от ключа) — теряется только распознавание повтора уже terminal-операции.
- **Concurrent requests с разными планами**: поскольку "одна логическая операция" определена per-user (не per-plan), второй одновременный запрос на другой план присоединяется к уже активной операции первого плана, а не создаёт параллельный attempt.
- **Ответ клиенту для присоединившегося запроса**: новый исход `duplicate` (`POST /api/purchase` → HTTP 409), возвращаемый только когда операция, к которой присоединился запрос, ещё не завершена (`initiated`/`processing`); если к моменту ответа операция уже стала terminal, клиент получает её фактический результат (succeeded/declined/timed_out/errored) напрямую, без отдельного `duplicate`-статуса.
- **"Зависший" `initiated`** (Stage 11): если attempt создан, но не дошёл до `processing` из-за прерывания (crash, необработанное исключение), он остаётся активным и блокирует constraint выше. Добавлено ровно одно новое ребро в state machine (раздел 11) — `initiated -> errored` — и reap-логика: при обнаружении non-terminal attempt старше `STALE_ACTIVE_ATTEMPT_MS` (60 секунд — заведомо больше, чем максимальная задержка fake PSP) он переводится в `errored` (с `purchase_failed` аналитикой), после чего создаётся новый attempt для текущего запроса. Тот же порог покрывает и гипотетически зависший `processing`.

## 14. Paywall requirements

### Три плана

Конкретные план(ы) фиксируются здесь как illustrative-но-однозначные данные (нужны, чтобы paywall был реализуем без дополнительных решений); это не подтверждённая официальная тарифная сетка ChaChat (публичной тарифной сетки нет — см. product-research раздел 8), а правдоподобные для тестового задания значения:

| Plan | Цена | Период | Позиционирование |
|---|---|---|---|
| Weekly | $6.99 | 7 дней, авто-продление | Попробовать без обязательств |
| Monthly | $14.99 | 30 дней, авто-продление | "Most Popular" — обычный выбор |
| 3 Months | $29.99 | 90 дней, авто-продление | "Best Value" — наименьшая цена в пересчёте на неделю |

Различие между планами — исключительно длительность/цена/пометка популярности; конкретные feature-gating различия (например "voice только в Monthly+") не вводятся как факт, поскольку не подтверждены product research — copy может ссылаться на общую ценность продукта (memory/voice/image generation/custom characters), одинаковую для всех планов.

### Payment form

Поля: card number, expiry, CVC. Без внешнего redirect — форма встроена в Paywall.

### Состояния интерфейса

`initial → plan_selected → submitting → success | decline/error | timeout → retry (возврат к submitting через новый submit)`.

- **initial**: ни один план не выбран, форма недоступна/неактивна для submit.
- **plan_selected**: план выбран, форма доступна для заполнения и отправки.
- **submitting**: форма отправлена, идёт обработка (соответствует `processing`), Purchase CTA заблокирован от повторных нажатий, но блокировка UI — не единственная защита (раздел 13).
- **success**: переход на Install.
- **decline/error**: понятное сообщение, форма и выбор плана сохраняются, Purchase CTA снова активен.
- **timeout**: понятное сообщение (не бесконечный spinner), возможность retry.
- **retry**: повторная отправка формы после decline/timeout/error, инициирует новую логическую payment operation (раздел 13).

### Что пользователь должен понимать перед покупкой

- Что именно даёт подписка (継続 отношения с персонажем, память, доступные форматы общения — на основе confirmed value props).
- Что план — это подписка с указанным периодом и авто-продлением, а не разовый платёж (характер плана прозрачен).
- Что повторный клик по Purchase безопасен и не приведёт к повторному списанию (прямое отражение гарантии из раздела 13 в UX-язык, например поясняющий текст рядом с CTA или в состоянии submitting).
- Что оплата — тестовая (fake PSP), это должно быть отражено в копирайтинге как элемент, снимающий тревогу перед вводом карты, без притворства, что это реальный платёж.

## 15. Quiz requirements

Количество вопросов: 5 (в допустимом диапазоне 3–7). Минимум два — product-aware, остальные — сегментационные, все ответы single-choice.

1. **(сегментация)** "What are you hoping to find in an AI companion?" — Someone to talk to / A creative co-writer for stories / A companion who feels romantic / Just curious, exploring
2. **(product-aware, memory)** "ChaChat's AI characters remember details from your past conversations. How important is it to you that a companion remembers what you've told them before?" — Very important / Somewhat important / Not important
3. **(сегментация, жанр)** "What kind of characters or stories interest you most?" — Fantasy & adventure / Romance / Everyday conversation / Something else
4. **(product-aware, voice)** "ChaChat also supports voice conversations, not just text. Would you like to talk with your AI character by voice?" — Yes, I'd love that / Maybe, I'll try it / I prefer text only
5. **(сегментация, частота)** "How often do you imagine chatting with your AI companion?" — Multiple times a day / Once a day / A few times a week / Just occasionally

Требования к поведению (не UI-реализация):

- Каждый ответ сохраняется сразу при выборе (не только при финальном submit квиза).
- Каждый шаг генерирует `screen_view` (screen=quiz, step) — аналитически отслеживаем per-question drop-off.
- Вопросы 2 и 4 используют только подтверждённые фичи (memory, voice) — ничего не придумано сверх product-research.
- Тон — нейтральный, без явного sexual framing, несмотря на 18+ позиционирование продукта.

## 16. Install requirements

### Условия доступа

Install доступен исключительно при наличии у текущей identity (visitor → user) хотя бы одной purchase со статусом succeeded. Проверка выполняется на сервере при каждом заходе на маршрут Install, не только один раз в момент оплаты.

### Содержимое

- Confirmation успешной покупки (какой план куплен).
- CTA/ссылка на приложение — используются реальные публичные точки входа ChaChat (App Store / web app), а не фиктивные ссылки.
- Информация про email — сообщение о том, что доступ/детали привязаны к указанному email (без реальной отправки письма, раздел 1).

### Поведение при попытке попасть на Install без успешной покупки

Graceful redirect (не error-страница, не "403") на Paywall (или Start, если email вовсе не известен для текущей identity) — попытка прямого захода по URL без покупки не считается ошибкой пользователя, а просто недопустимым состоянием funnel, из которого пользователь корректно возвращается в подходящую точку funnel.

## 17. Error handling

Общие принципы (сквозные для всех экранов):

- **Validation errors** (например невалидный email) — показываются inline, не прерывают сессию, не требуют перезагрузки экрана.
- **Network/server errors** — контролируемое состояние ошибки с возможностью повтора там, где повтор безопасен (раздел 13 для payment); никогда не оставляют пользователя перед бесконечным spinner без обратной связи.
- **Идентичность/linking ошибки** (сбой при создании/линковке user на экране Email) — пользователь остаётся на экране Email, может повторить отправку; данные quiz не теряются.
- **Payment ошибки** (decline/timeout/error) — раздел 11–12; никогда не оставляют БД в неконсистентном состоянии (раздел 11, "Консистентность БД").
- **Попытка недопустимого перехода** (прямой заход на экран, для которого не выполнены предпосылки) — graceful redirect на корректный экран funnel, не "жёсткая" ошибка (раздел 4, 16).
- Любое отклонение от happy path, где это осмысленно для аналитики, отражается соответствующим событием (`purchase_failed`, и т.п.) — ошибки не только показываются пользователю, но и остаются наблюдаемыми в БД.

## 18. Acceptance criteria

### Funnel
- [ ] Полный happy path `Start → Quiz → Email → Paywall → Payment → Install` проходим end-to-end.
- [ ] Недопустимые прямые переходы (раздел 4) блокируются с graceful redirect, а не ошибкой/крашем.

### Identity
- [ ] Новый anonymous visitor создаётся при первом визите и накапливает историю до email.
- [ ] Anonymous → новый email создаёт ровно одного нового user, история visitor становится его историей.
- [ ] Anonymous → существующий email НЕ создаёт нового user, привязывает текущего visitor к найденному user, не теряет и не дублирует его текущую anonymous-историю и существующие purchases.
- [ ] Повторная отправка того же email идемпотентна (без дублирующих связей).
- [ ] Повторный визит уже identified пользователя с существующей successful purchase направляется сразу на Install.

### Attribution
- [ ] UTM/referrer/landing URL фиксируются при первом запросе новой session и не перезаписываются последующей навигацией в её рамках.
- [ ] Canonical acquisition attribution пользователя вычислима как attribution его самой ранней session (SQL-запросом).

### Analytics
- [ ] Все события из раздела 10 записываются в PostgreSQL с обязательными идентификаторами.
- [ ] По данным БД восстановима полная история конкретного user: откуда пришёл, какие экраны видел, какие ответы дал, какой email указал, какой plan выбрал, чем закончилась оплата.
- [ ] Funnel/drop-off/conversion считаемы SQL-запросами без дополнительной логики приложения.

### Payments
- [ ] Success, decline, timeout воспроизводимы детерминированно через задокументированные тестовые карты.
- [ ] Payment state machine (раздел 11) соблюдается: нет переходов из терминальных состояний, purchase создаётся только вместе с succeeded.
- [ ] Retry после decline/timeout/error разрешён и создаёт новый payment_attempt.
- [ ] Install доступен исключительно при наличии succeeded purchase.

### Concurrency
- [ ] Double-click не создаёт вторую succeeded purchase.
- [ ] Две вкладки, инициирующие оплату одновременно, не создают вторую succeeded purchase.
- [ ] Refresh во время обработки не создаёт новый attempt/purchase, отражает фактическое состояние.
- [ ] Повторная отправка того же запроса (в т.ч. эмулирующая network failure) не создаёт вторую succeeded purchase.
- [ ] Ни при каком из вышеперечисленных сценариев не появляется более одной succeeded purchase на одну логическую операцию.

### Docker
- [ ] После clean checkout `docker compose up` поднимает приложение и PostgreSQL, миграции применяются автоматически, без ручной установки зависимостей вне контейнеров.

### Documentation
- [ ] В репозитории присутствуют: `docs/spec.md`, agent instructions (AGENTS.md), README (с SQL-примерами и test card rules), prompts/skills/commands (если использовались).

## 21. Summary — принятые решения / оставлено на реализацию / обязательные требования

### Ключевые архитектурные решения, зафиксированные в этой спецификации

- Anonymous-историю держит отдельная устойчивая сущность **visitor** (не сама session и не сразу user) — это то, что делает возможным связывание с existing user без потери истории и без "merge" двух полноценных пользователей.
- Anonymous → existing email = **связывание** (`visitor.user_id` указывает на найденного user), а не создание дубликата и не полноценный merge — согласовано с предпочтением из плана задания.
- Attribution — атрибут **session**, canonical attribution пользователя = attribution его самой ранней session (first-touch по всей истории, никогда не перезаписывается).
- Одна логическая payment operation определена как "не более одного нетерминального payment_attempt на user одновременно" — на этом определении построены все concurrency-гарантии (double-click/two tabs/refresh/repeated request), это архитектурно необходимое решение, а не деталь реализации.
- Purchase создаётся строго атомарно вместе с переходом attempt в succeeded; payment attempt и purchase — разные сущности (различие необходимо, чтобы отличать "любую попытку" от "успешную покупку" для аналитики и для идемпотентности).
- Install доступен исключительно и всегда при наличии succeeded purchase, проверяется на каждый заход, а не только сразу после оплаты.

### Оставлено на этап реализации

Полный список — раздел 20 (ORM/DB client, конкретный механизм cookie/identity, конкретный механизм idempotency lock/constraint, точные значения таймаутов и тестовых карт, визуальный UI).

### Обязательные требования из исходного задания, отражённые в документе

Funnel из 6 экранов; PostgreSQL; Docker Compose с автоматическими миграциями; anonymous → identified user с корректной обработкой existing email; сохранение UTM/referrer/landing URL; запись meaningful funnel events в SQL, пригодных для funnel-аналитики; три payment plans с custom payment form без внешнего redirect; fake PSP с детерминированными success/decline/timeout; отсутствие дублирующих successful purchases при double-click/two tabs/refresh/repeated request, с гарантией на уровне backend/DB; README с SQL-примерами и test card rules; agent instructions в репозитории.
