# План выполнения тестового задания — ChaChat Funnel

## Цель

За ограниченное время реализовать законченный web funnel для ChaChat, который можно запустить на чистом окружении через Docker, пройти от landing page до успешной или неуспешной оплаты и проверить всю историю пользователя и funnel events в PostgreSQL.

Главный приоритет — не визуальная полировка, а корректность пользовательского сценария, данных, аналитики, платежной логики и обработки edge cases.

Целевой срок — до 48 часов.

План рассчитан примерно на 36 часов основной работы и оставляет значительный резерв на исправления, интеграционные проблемы и финальную проверку.

# Этап 1. Спецификация и архитектурные решения

**Цель:** определить поведение системы до начала реализации.

Создать основной документ спецификации в репозитории.

### Технологический стек

Для проекта выбрать и зафиксировать:

- Next.js;
- TypeScript;
- Next.js App Router;
- PostgreSQL;
- Docker Compose.

Next.js выбран как основной framework, поскольку тестовое требует полноценный full-stack web funnel с backend logic, API/server-side operations и контролем payment flow.

Конкретный ORM/database access layer, структура модулей и прочие детали реализации не фиксируются заранее без необходимости.

### В спецификации определить

#### Funnel

Последовательность:

```text
Start
  ↓
Quiz
  ↓
Email
  ↓
Paywall
  ↓
Payment
  ↓
Install
```

Определить поведение каждого экрана и допустимые переходы.

#### User identity

Описать жизненный цикл:

```text

        ↓
session/history
        ↓
email
        ↓
identified user
        ↓
purchase
```

Отдельно описать:

- первый визит;
- повторный визит;
- ввод нового email;
- ввод email существующего пользователя;
- сохранение истории anonymous visitor.

#### Identity merge/linking

Для случая, когда введённый email уже существует, заранее определить конкретное ожидаемое поведение.

Требование:

> История текущего anonymous visitor не должна теряться или превращаться в отдельного дублирующего пользователя.

Определить:

- какая identity становится основной;
- что происходит с текущей session;
- что происходит с attribution;
- как сохраняются quiz answers;
- как сохраняются events;
- как обрабатываются уже существующие purchases;
- что происходит при повторном выполнении операции;
- какие ограничения БД должны сохраняться.

Предпочтительная концепция — связывание anonymous history с существующим identified user, а не общий механизм слияния двух полноценных пользователей, если для этого нет необходимости.

#### Attribution

Определить, какие данные сохраняются при первом посещении:

- UTM parameters;
- referrer;
- landing URL;
- необходимые данные сессии.

#### Data model

Определить необходимые сущности и связи между ними.

Модель должна поддерживать:

- пользователей;
- anonymous visits/sessions;
- quiz answers;
- funnel events;
- plans;
- purchases;
- payment attempts или эквивалентную структуру, если она необходима.

#### Analytics

Определить:

- список событий;
- момент возникновения каждого события;
- идентификаторы, связывающие событие с пользователем и/или сессией;
- свойства событий;
- требования к данным, позволяющим строить funnel analysis.

#### Payments

Определить:

- жизненный цикл purchase/payment;
- успешную оплату;
- decline;
- timeout;
- повторную попытку;
- ошибки;
- поведение после refresh;
- поведение при повторной отправке.

#### Concurrency

Зафиксировать ожидаемое поведение для:

- double-click;
- двух вкладок;
- refresh во время payment;
- повторной отправки одного payment operation.

Главное требование:

> Один пользователь не должен получить две покупки вследствие повторной или конкурентной отправки одного платежного действия.

Механизм реализации идемпотентности не фиксировать заранее без необходимости. Важно обеспечить гарантированный результат на уровне backend/database.

#### Acceptance criteria

Для каждого критического сценария определить наблюдаемый ожидаемый результат.

# Этап 11. Purchase flow и concurrency

**Цель:** обеспечить корректность покупки при повторных и конкурентных запросах.

Это один из критических этапов проекта.

### Проверить сценарии

#### Double-click

Два почти одновременных purchase requests не должны создать две покупки.

#### Two tabs

Две вкладки не должны привести к двум покупкам из одного действия.

#### Refresh

Refresh во время обработки payment не должен создать новую покупку.

#### Retry

После decline пользователь должен иметь возможность повторить оплату.

#### Repeated request

Повторная обработка одного payment operation должна приводить к корректному результату без дублирования покупки.

### Требование

Защита от race conditions должна обеспечиваться на уровне backend/database, а не только пользовательского интерфейса.

### Результат

Purchase flow остаётся консистентным при конкурентных запросах.

**Оценка:** 5 часов.

# Этап 12. Payment failure handling

**Цель:** корректно обработать все предусмотренные результаты fake PSP.

### Decline

- понятная ошибка;
- purchase не считается успешной;
- пользователь остаётся в funnel;
- можно повторить оплату.

### Timeout

- отсутствие бесконечного spinner;
- понятное состояние;
- возможность корректно продолжить/retry в соответствии с payment state.

### Unexpected error

- controlled error;
- состояние БД не должно становиться неконсистентным.

### Success

- успешная purchase;
- корректные analytics events;
- переход на Install.

**Оценка:** 1.5 часа.

# Принцип работы с AI-агентами

Проект не должен превращаться в попытку реализовать все возможные production-функции.

Каждая задача должна отвечать конкретному требованию тестового или существенно повышать надёжность уже реализованного требования.

Большие этапы следует разбивать на небольшие самостоятельные задачи для AI-агентов.

Для каждой задачи агенту передаются:

- цель;
- необходимый контекст;
- ограничения;
- текущее состояние;
- критерии готовности.

Способ реализации не следует заранее диктовать агенту без необходимости. Архитектурное решение должно выбираться на основании требований проекта и текущего состояния репозитория.

После каждого крупного этапа выполняется промежуточная проверка. Ошибки не откладываются до финального QA.

Главный критерий завершения — не количество реализованных функций, а возможность с чистого окружения запустить funnel, пройти его, воспроизвести успешный и неуспешный payment flow, проверить отсутствие дублирующих покупок и получить из PostgreSQL полную аналитическую историю пользователя.
