## 1. ChaChat — product understanding

ChaChat — мобильно-веб приложение для общения с AI-персонажами (companion / roleplay chat), разработчик — Neiro.AI. Доступно на web, iOS, Android.

Подтверждённые источниками возможности:

- **Discover AI characters** — библиотека готовых AI-персонажей с разными личностями, внешностью, "мирами"/бэкграundами (fantasy, original characters, adventure/story settings).
- **Custom character creation** — пользователь может создать собственного AI-персонажа (личность, манера речи, история) и опционально поделиться им с другими пользователями (community sharing).
- **Text chat with memory** — персонажи "запоминают" детали предыдущих разговоров, что должно делать диалог более последовательным и продолжительным во времени.
- **Voice conversations** — голосовые звонки с персонажем (несколько вариантов голосов).
- **AI image generation** — генерация изображений, связанных с контекстом разговора/историей.
- **Interactive storytelling / roleplay** — совместное построение сюжета, ролевые сценарии.
- **Expressive actions** ("hugs and kisses" и т.п.) как элемент эмоционального взаимодействия внутри чата.
- Виртуальная валюта ("gems") продаётся пакетами — используется как микротранзакционная модель поверх подписки.

Возрастной рейтинг в App Store — **18+**, категория — Lifestyle. Это прямо указывает, что часть контента ориентирована на "spicy"/romance-роллплей, не только на нейтральные "AI friends".

**Не подтверждено источниками (не использовать как факт в quiz/paywall):** конкретные модели ИИ под капотом, точные лимиты бесплатного тарифа, наличие групповых чатов, интеграция с внешними платформами, языковая поддержка помимо английского.

## 2. Target user and value proposition

**Целевая аудитория** (по позиционированию и возрастному рейтингу): взрослые пользователи (18+), ищущие один или несколько сценариев:
- эмоциональная компаньонская переписка ("AI friend/soulmate");
- романтический/спич roleplay;
- творческое соавторство — интерактивные истории, фэнтези-сценарии;
- создание и кастомизация собственных персонажей как форма самовыражения.

**Основная ценность продукта:**
- ощущение персонализированного, "помнящего" собеседника, доступного в любое время;
- творческая площадка (персонажи, истории, изображения) без необходимости писать код или использовать сложные инструменты;
- эскапизм/развлечение через ролевые сценарии и фэнтези-сеттинги;
- (потенциально) снижение одиночества за счёт компаньон-опыта — это частый мотив категории AI companion apps, но в ChaChat конкретно не подтверждён отдельным заявлением компании, поэтому в quiz/paywall стоит формулировать аккуратно, не как медицинское/терапевтическое обещание.

**Что пользователь делает внутри продукта:** выбирает или создаёт AI-персонажа → ведёт текстовый и/или голосовой диалог → участвует в ролевых сценариях/историях → получает сгенерированные изображения по мотивам разговора → при желании делится своим персонажем с сообществом.

**AI characters/bots в контексте продукта** — это не служебные ассистенты (не "AI для задач"), а персонажи с личностью, историей и манерой речи, к которым пользователь возвращается ради продолжающихся отношений/сюжета, а не ради разового ответа на вопрос.

## 3. Test assignment requirements (систематизировано по категориям)

### Product / UX
- Funnel: Start → Quiz → Email → Paywall → Payment → Install.
- Экраны должны иметь понятные переходы и допустимые состояния (в спецификации).

### Funnel
- 6 последовательных экранов, каждый со своим назначением и логикой перехода.

### User identity
- Anonymous visitor должен существовать до email.
- Переход anonymous → identified user через email.
- Обработка случая "email уже существует" — обязательное требование.

### Attribution
- Сохранение UTM parameters, referrer, landing URL при первом визите.

### Analytics
- Все значимые события funnel сохраняются в SQL database (не только в UI/клиентском логировании).

### Database
- PostgreSQL preferred.
- Данные должны поддерживать построение funnel-аналитики (значит — связность event↔session↔user).

### Payments
- Три payment plans.
- Собственная (custom) payment form — не редирект на внешний checkout.
- Fake payment processor с исходами success / decline / timeout.
- Purchase records должны существовать в БД.

### Concurrency / idempotency
- Double-click не должен создавать дублирующую покупку.
- Refresh во время оплаты не должен создавать дублирующую покупку.
- Две открытые вкладки не должны привести к двум покупкам.
- Нет дублирующих purchases ни при каком из этих сценариев.

### Docker
- Docker Compose — весь проект поднимается из чистого состояния без ручной установки зависимостей вне контейнеров.

### Documentation
- Specification должна существовать **до** начала разработки.
- README должен включать SQL queries (аналитические) и test card rules (детерминированные правила fake PSP).

### AI workflow
- Agent instructions (файл вроде AGENTS.md) — описывает, как AI-агенты должны работать с проектом.

## 4. Implicit engineering requirements

Ниже — то, что задание подразумевает, но не формулирует напрямую. Указано, **что система должна гарантировать**, без предложения конкретной реализации.

**Anonymous visitor**
- Должна существовать возможность идентифицировать одного и того же анонимного посетителя между запросами/страницами в рамках одной сессии (иначе "anonymous → user" не имеет смысла как непрерывная история).
- Anonymous-состояние должно переживать переход между экранами funnel (quiz answers, посещённые шаги) до момента ввода email.

**Существующий email**
- Система должна каким-то образом отличать "новый email" от "уже существующего email" при отправке email-формы.
- Должно быть гарантировано, что ввод существующего email не создаёт второго дублирующего пользователя и не приводит к потере текущей anonymous-истории.

**Сохранение полной истории пользователя**
- Все действия (quiz-ответы, просмотренные экраны, попытки оплаты) должны быть восстановимы по единой пользовательской истории после идентификации — то есть связь anonymous-активности с итоговым identified user не должна теряться.

**Повторный визит**
- Система должна как-то отличать "новую" сессию/визит от продолжения предыдущей, иначе attribution "первого визита" и повторные visits будут неразличимы либо будут неверно перезаписываться.

**Payment state**
- У purchase/payment должен быть жизненный цикл с несколькими состояниями (как минимум: инициировано, в процессе, успех, отказ, таймаут/ошибка) — иначе невозможно корректно обработать retry, refresh и concurrency-требования.
- Должно быть определено, что значит "одна платёжная операция" — иначе double-click/2 tabs/refresh не с чем сравнивать для дедупликации.

**Fake PSP**
- Результат (success/decline/timeout) должен быть детерминированным и воспроизводимым (т.к. README обязан содержать test card rules) — то есть логика не может быть случайной без предсказуемого триггера.
- Таймаут — это тоже валидный конечный результат, который должен обрабатываться, а не зависать бесконечно.

**Double-click / refresh / two tabs / повторная отправка**
- Все четыре сценария — это по сути один и тот же класс требования: система должна гарантировать не более одной успешной покупки на одну "логическую" попытку оплаты, независимо от того, сколько раз клиент физически отправил запрос.
- Это должно обеспечиваться на backend/DB уровне, а не только отключением кнопки в UI (UI-блокировка недостаточна и явно не покрывает refresh/2 tabs).

**Purchase duplication**
- Нужен способ отличить "повторную попытку после decline" (это legitimate — должно быть разрешено) от "дублирующего запроса той же попытки" (должно быть запрещено). Это два разных сценария, которые легко перепутать в реализации.

**Analytics funnel queries**
- Схема данных должна допускать построение когортных/последовательных запросов (funnel steps, drop-off, conversion, revenue by plan, acquisition by UTM) — то есть события должны иметь достаточно контекста (кто, когда, в рамках какой сессии/попытки) для JOIN-ов между таблицами, а не быть плоским логом без связей.

## 5. Questions to resolve in the specification

(Список вопросов — без ответов, для следующего этапа)

**Identity**
1. Что технически означает "anonymous visitor" на уровне спецификации (сущность/сессия) и чем она отличается от "визита"/"сессии"?
2. Какая identity становится основной при вводе существующего email — текущий anonymous-контекст привязывается к существующему user, или создаётся какой-то другой механизм связывания?
3. Что происходит с quiz-ответами, событиями и attribution текущей anonymous-сессии в момент привязки к существующему user?
4. Как обрабатываются уже существующие purchases найденного user при повторном визите — показываются ли они, влияют ли на paywall?
5. Что считается "повторным визитом" против "продолжением той же сессии", и как это влияет на attribution (перезаписывается ли first-touch)?

**Attribution**
6. Какие именно данные сессии обязательны, кроме UTM/referrer/landing URL (user agent, device, IP, timestamp)?
7. Attribution сохраняется по правилу first-touch, last-touch, или иначе?

**Analytics**
8. Какие события считаются meaningful (полный список) и в какой момент каждое из них возникает?
9. Какие обязательные и опциональные свойства должны быть у события (event properties)?
10. Какие идентификаторы обязаны присутствовать в каждом событии, чтобы связать его с user/session/attempt?

**Payments / concurrency**
11. Какие состояния имеет payment (полный список состояний и допустимые переходы между ними)?
12. Что именно считается "одной payment operation" — по какому признаку два запроса признаются дублирующими друг друга?
13. Как должна вести себя система, если клиент не получил ответ (network drop) при том, что backend уже обработал операцию?
14. Разрешено ли и как инициировать новую попытку оплаты после decline/timeout (новая payment operation или продолжение старой)?

**Data model / прочее**
15. Какие сущности и связи обязательны в data model (users, sessions, quiz answers, events, plans, purchases, payment attempts)?
16. Какие данные обязаны сохраняться при выборе plan и что считается "выбором" plan как событием?
17. Что должно происходить с состоянием БД при unexpected error фейкового PSP (частичная запись, компенсирующая операция, и т.п. — на уровне гарантии, не реализации)?

## 6. Potential quiz questions

Черновые варианты (3–7 итоговых будут выбраны на этапе спецификации). Специально не придумано ничего, что не подтверждено источниками.

**Вопросы о самом ChaChat (product-aware, объясняют/проверяют продукт):**
1. "В ChaChat AI-персонажи запоминают детали ваших прошлых разговоров. Насколько важно для вас, чтобы собеседник помнил контекст предыдущих бесед?" — раскрывает feature "memory", объясняя пользователю ценность до paywall.
2. "Кроме текстового чата, ChaChat поддерживает голосовые звонки с AI-персонажем. Хотели бы вы общаться голосом, а не только текстом?" — знакомит с voice-функцией.
3. "В ChaChat можно создать собственного AI-персонажа с уникальной личностью и историей. Вы бы предпочли выбрать готового персонажа или создать своего?" — знакомит с character creation.

**Вопросы о интересах/use case пользователя (сегментация, не выдуманные функции):**
4. "Какой тип историй/персонажей вам ближе: фэнтези-приключения, романтика, повседневное общение или что-то своё?" — сегментация по жанрам, соответствует реально существующим категориям персонажей.
5. "Что вы ищете в первую очередь: собеседника для развлечения, партнёра для совместного сочинения историй, или кого-то, с кем можно просто поговорить?" — help understand mindset без придумывания фич.
6. "Как часто вы бы хотели общаться с AI-персонажем: несколько раз в день, раз в день, пару раз в неделю?" — engagement-сегментация, полезна для paywall-нарратива ("для регулярного общения выгоднее подписка").
7. "Что для вас важнее всего в AI-собеседнике: он помнит вас, у него яркая индивидуальность, или он выглядит и говорит максимально реалистично?" — priorities, может направлять на paywall value props (memory / personality / voice&image realism).

Замечание: т.к. приложение имеет рейтинг 18+ и романтический/roleplay контент — вопросы должны оставаться нейтральными по тону в quiz (без явного sexual framing), т.к. это тестовое задание, а не продакшн-маркетинг; итоговый тон подтверждается на этапе спецификации.

## 7. Paywall product considerations

**Ценность, которую стоит подчеркнуть:**
- Персонажи, которые помнят пользователя (continuity) — это единственная явно подтверждённая "premium-ощущаемая" фича (memory).
- Расширенные форматы общения — voice calls, image generation — как естественный "upgrade" от базового текстового чата.
- Возможность создавать и кастомизировать собственных персонажей без ограничений.

**Пользовательский результат, который можно "продавать":**
- Не разовый ответ, а *продолжающиеся отношения/сюжет* с персонажем — акцент на "твой персонаж, который тебя помнит и развивается вместе с тобой", а не на разовую транзакцию.

**Элементы, которые должны присутствовать на paywall (по требованиям задания + product logic):**
- Три четко различимых плана (название, цена, условия/период).
- Понятная разница между планами (что даёт более дорогой план — это должно решаться в спецификации, но в самом paywall разница обязана быть explicit).
- Payment form (card number/expiry/CVC) прямо на странице, без внешнего редиректа.
- Loading / success / error состояния, видимые пользователю.
- Что-то, снимающее opasenie перед вводом карты (даже в тестовом задании стоит показать элемент доверия — например, пояснение про безопасность/тестовый режим).

**Сомнения, которые стоит снять перед покупкой:**
- "А что если это не то, что я ожидал(а)?" → чёткое описание, что именно дает подписка.
- "А не спишут ли с меня деньги повторно?" → это прямая проекция требования "no duplicate purchases" в продуктовый UX-язык — должно быть видно пользователю, что повторный клик безопасен.
- "Могу ли я отменить/это разовый платёж или подписка?" → характер плана (subscription vs one-time) должен быть прозрачным — решается в спецификации.

## 8. Risks and ambiguities

- **Публичная информация о ChaChat ограничена** — нет официального pricing page с чётким описанием, что именно входит в каждый план; цифры из App Store (monthly/annual/lifetime/gems) дают ориентир, но не являются "официальной" тарифной сеткой продукта и не обязаны буквально копироваться в тестовое задание.
- **18+ рейтинг и romance/roleplay позиционирование** создают риск, что quiz/paywall может случайно скатиться в неуместный для тестового задания тон — стоит явно зафиксировать в спецификации нейтральный, "safe for review" тон контента.
- **Реальные технические детали продукта (backend, память, лимиты) не публичны** — не должны использоваться как основа для реализации функциональности, только как основа для правдоподобного текста quiz/paywall.
- **Attribution/identity требования пересекаются с открытыми архитектурными вопросами** (double-click, two tabs, existing email) — это наиболее рискованная с точки зрения оценки часть задания и требует однозначных решений в спецификации до кода.
